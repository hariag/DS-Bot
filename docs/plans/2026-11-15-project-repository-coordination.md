# 跨群项目协调与仓库新鲜度

## 问题

群会话彼此独立，可以同时工作。任务板能记录任务 owner 和跨群只读授权，但目前没有项目映射，也没有指定共享项目的项目经理。`remoteChangeWatch` 每 15 分钟读取 GitHub 提交并把变更记在个人看板，但不会更新本地 checkout 或工作树。

## 第一阶段行为

- 同一项目的各群 notice 记录一致的项目 ID、仓库、集成分支、唯一项目经理 Bot 和可达路由。PM 必须在每个协作群，或 notice 必须指定所有参与 Bot 都可访问的协调群。字段或路由缺失、有歧义时，先请群管理员补齐，不猜测群之间的关系。
- 同一逻辑任务跨群和私聊使用同一个 task ID。每个代码切片有唯一 owner、明确写入范围和基准 commit。
- 接手共享仓库任务、每次提交或合并前，以及持续工作每 30 分钟，检查工作树和 HEAD；在有权限时 fetch 集成 ref 并记录检查时间与 SHA。合并后核对 HEAD。没有 fetch 权限时，只能使用有可信来源及检查时间的 tracking ref；ref 不够新或时间不明时暂停共享写入，请项目经理刷新。
- 只对 upstream 已明确且严格落后的干净分支执行 fast-forward。工作树有未提交改动、分支已分叉或 upstream 不明时保留原状，由项目经理协调；禁止自动 pull、reset、rebase 或覆盖。
- 冲突指写入路径重叠、契约或验收规则不兼容，或依赖顺序互斥。只停止冲突部分，并经可达路由向项目经理发一条可执行的交接，附两个 task ID、群、负责人、仓库/ref、基准与当前 SHA、受影响路径、证据、选项和建议。PM 不可达时保持冲突阻塞并请群管理员补路由；无冲突的独立工作可继续。
- 代码按短小且已核对的切片提交。交接提供基准与结果 SHA、修改路径和验证记录。

## 限制与后续切片

本阶段是共享提示词约定，不构成 Git 权限边界，不会自行调度 Bot、定时 fetch、自动检查本地工作树或自动合并。现有远端变更巡检只观察 GitHub 提交；它不掌握各组的本地 checkout 路径，也不负责同步工作树。若没有可信 ref 或定期任务回合，不能声称本地代码已是最新，也不能声称 30 分钟运行时 SLA 已保证。

下一阶段如需真正自动刷新，须先提供显式项目登记（项目 ID、仓库、集成 ref、受管理的本地目录、唯一协调者和授权），并单独设计只更新 tracking refs 的轮询与安全 fast-forward。不得从相似群名推断项目映射，不得在未登记的任意目录运行 Git；脏工作树、分叉和权限不足均只报告并交由项目经理处理。

系统不会自动关联群或指定项目经理；用户须在参与群的 notice 中填写相同项目元数据。
