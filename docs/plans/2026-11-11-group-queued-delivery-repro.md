# 排队群消息的逐条派发：缺陷与修复设计

## 复现

在 `ds-bot/` 运行 `node test/reproduce-queued-group.mjs`。脚本从现有 `group-work.test.js` 取隔离 mock host，在临时目录准备测试数据，串行写入 `@Writer first request`、`@Tester second request`，调用一次 `group_relay`。预期两个收件者各得到自己的调用；实际 Tester 得到一次调用、Writer 为零。脚本把该预期失败识别为 `REPRODUCED`，不属于默认测试套件。临时测试文件与 mock home 在结束时清理。

### 保存失败和锁重取补充复现

2026-11-11T15:30:16+08:00，在隔离 mock 环境额外验证：`node test/reproduce-group-save-loss.mjs` 注入保存异常后，两条待派发 post 在派发前已从内存队列消失；`node test/reproduce-group-adopt-race.mjs` 模拟锁重取并采用新 state 后，旧 room 的 post 不在新 state 且原队列已被消费。两个脚本的 `REPRODUCED` / exit 0 表示缺陷仍存在，并非测试对象已修复。真实运行环境未做故障注入。

2026-11-11T17:14+08:00，另以隔离 mock 环境运行 `node test/reproduce-group-drain-save-failure.mjs`，验证运行中轮次的 `drainRoomInbox` 在 state 保存抛错时仍从 Session inbox 删除消息并启动收件 Bot，保存异常被忽略。账本是否持久化是独立问题，此用例不证明外部副作用发生重复或丢失；它证明 state 保存失败没有阻断领取和派发。修复与重启验证须同时覆盖运行中 drain，不足以只覆盖下一轮的 `group_relay`。`REPRODUCED` / exit 0 表示缺陷仍存在。

尝试过的局部方案将队列保留到 required save 成功并串行化同群入账；它在上述 lock reclaim/adopt 情况下仍会写旧 room、保存新 state 后消费队列，且异步账本写入失败不会由 state save 证明。因此已撤回候选代码；不能把保存成功视为消息与账本均已持久化。

## 根因与边界

- `src/host/groups.js` 的 `group_relay` 把排队帖子依次写进群日志，却仅由最后一个合格 opener 决定本轮收件人。前面帖子可能可见，但其明确指定的收件人未被独立派发。
- `callIn` 会将同一等待中成员的多次调用合并，并更新 note、by 和 batch；如果仅追加收件人，同一 Bot 的独立任务及不同发起者的归属会丢失。成员看到的内容又依赖群日志的 seen 游标，而非固定某条帖子的独立任务。
- 当前 `roomInbox` 是内存队列，relay 先整体取出并删除，再处理落账和派发。增加单纯的内存重试无法证明异常或进程中断后的可靠性。此处仅说明代码路径；运行实例是否发生过相同丢派，尚未核验。

## 拟议方案

1. 建立持久的群帖子派发记录，为每个来源消息及每个收件人分配稳定 ID。记录原群、原序号、发送人、正文与附件引用、@ 解析结果、所属工作及回执关系；事件和派发状态须有可恢复的持久化顺序。沿用已经落账的群消息，不复制或改写历史消息。
2. 以原 post 为派发单位，从早到晚推进；每个指定收件人的调用独立记录。同一个 Bot 的不同 post 保持先后，不用 waiting slot 的覆盖来合并。只有业务显式标识同一工作，且不跨审批、依赖或顺序边界时，才允许另行实现补充更新。
3. 在持久化 outbox 中记录待派发、已接收和最终结果，使用稳定 exchange ID 与接收方的持久去重记录对齐。进程中断后先核对接收和结果，再按状态恢复；不能只凭内存标志或发送回执判定业务已经完成。状态写入失败时保留待处理项目并显示异常。
4. 回复、batch、工作树、goal、暂停状态、附件及群日志位置均关联原 post/收件人。已有群 round、普通群消息、排队附件、@all、Bot 转发、reportBack、可见性、用户中止和延迟结果保持原约定；迁移仅对可确认未派发的新记录进行重放，不能自动重播旧日志猜测遗漏。
5. 完全一次的外部副作用依赖目标系统支持幂等键或原子事务。框架可提供持久投递、去重及结果对账，不能仅凭一次派发承诺外部动作恰好执行一次。

## 验收范围

在隔离 mock bench 上覆盖：两条消息分别 @ 不同成员；同一成员接收两条独立指令；不同发送人分别 @ 同一成员并收到正确回执；附件和长文本保持所属消息；@all、goal draft、已 called 消息与普通帖子混排；每一个持久化/入队/接收/回复边界中断重启；保存失败、只读主机、成员移除、取消、消息重复和并发重试。检查顺序、身份、无遗漏、无重复、结果归属和旧数据兼容。需再以真实环境的只读观测核对，不能用 mock 结果声明线上已修复。

## 独立实验

`ds-bot/src/host/group-outbox.js` 仅作为候选记录实验，提供暂存和查询，不接入当前派发，也没有发送、确认或重放接口。它记录来源 Session、消息 ID、splice 位置、内容和接收者；内容或来源位置冲突时拒绝覆盖，不把入库顺序视为已验证的来源顺序。相应隔离测试覆盖进程退出、事务中止、并发暂存、锁竞争和外部数据库保护。

外部 state.lock 检查与 SQLite 提交及路径操作不构成原子 fencing；完整 splice 水位、编辑/删除/插话对账、跨会话顺序、接收端屏障和外部动作幂等尚未实现。首次建库中断可能留下无身份标记的文件并拒绝自动恢复。该实验不能用于现网派发或声称端到端可靠。

## 最小跨框架改造与切换顺序

本节是 2026-11-11T17:17+08:00 的设计，**尚未实现或部署**；不改变前述未修复结论。代码核查范围为 DS Bot 本地 HEAD `478b652f01dae03269a511e834152b052e38add7` 与未提交工作区，以及本机 DeepSeek Harness `master` HEAD `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159` 的工作区。`ReactLoopInbox.remove` 当前使用带 `outcome: canceled` 的 splice，不能被当成可靠的群消息接收回执。仅将 remove 移到 `save` 之后，仍可能先写入异步群账本、再因 state 保存失败而在重试时重复落账；锁重取时也可能保存的是被 adopt 的新 state。停用运行中 drain、把消息留到下一轮也不足够：DSH 可能在一个步骤 claim 多条 nextStep，而现有 relay 仍只从最后一个 opener 选人。

1. **入口和单调水位**：扩展 DSH 的输入交接契约，在同一 Session 内用源 Session ID、消息 ID 和持久事件位置标识消息，保留原文、附件、来源、顺序、编辑及取消语义。消费方先从可完整重放的事件流建立候选；若事件段、连续水位或旧 Session 迁移映射缺失，标记该段待人工核对并停止自动投递，不能用 SQLite 插入顺序推测来源顺序。批量 claim 的每条消息均必须有独立标识和顺序。
2. **接收事务**：为 DSH 增加具名接收/claim，而不是调用表示取消的 remove；以原消息 ID 和版本做 compare-and-claim，使读取后被编辑、取消或移走的消息不能按旧内容派发。接收记录与 outbox 待派发记录需要共同提交于同一可恢复事务或采用明确的预写记录和启动对账协议；先落 outbox 再确认接收，进程停在两者之间时按稳定 ID 去重补齐。当前 `group-outbox.js` 仅是候选存储，未实现这个契约。
3. **单写者与派发**：在与派发记录相同的事务域验证可递增的 fencing token；不能用独立 `state.lock` 检查后再写 SQLite 假定原子。每个 post 和每个目标成员建立唯一派发 ID；按来源顺序在群内推进，并对同一成员保证依赖顺序。发件方、batch、回复归属与附件绑定原 post；不复用会覆盖先前任务的 waiting slot。成员接收端需用同一派发 ID 做持久去重，重复提交返回既有接收记录，不重新启动成员。接收记录与后续状态更新不构成外部操作恰好一次的证明。
4. **恢复和不确定状态**：明确区分候选、接收、已派发、成员已接收、终结结果和结果不明。记录提交或发送结果不确定时先按派发 ID 查询接收端；没有可靠接收记录或外部副作用证据时停在待核，不自动重放。对能提供幂等键的外部系统传递稳定业务键；其余写文件、网络和工具动作需独立核对，不能承诺业务副作用恰好一次。
5. **迁移与回滚**：先离线影子读取 Session 事件，输出有界水位、缺段和冲突清单，与现场 inbox/账本/工作记录逐 ID 对账，不发送或补发；旧数据状态不明继续人工核对。只在隔离环境完成故障注入，再以新版本号和明确切换水位对新消息启用，旧记录不可因缺状态自动重放。每个群一次仅允许旧或新派发器有写权限；切换前后验证持久屏障和单写者 fencing，回滚时冻结新入口并先对账所有未终结 ID，避免旧派发器接管后再次发送。实时切换、重启和历史消息修复需在实际环境验证其安全条件。
