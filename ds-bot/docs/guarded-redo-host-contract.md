# Guarded redo Host contract (WIP)

This is a review contract for an unfinished integration. The route is not installed by default. A redo remains unavailable until the original input, current scope, exact Agent/Session, durable journal and result delivery have all been verified. A user's explicit choice may repeat external side effects; it is not an exactly-once guarantee for those effects.

## Stable operation and admission

A user-confirmed operation binds one operation ID, original recovery ID, authenticated user and scope, original Bot and Session, original turn and input sequence, exact input ID and content digest, stable new message ID and admission ID, and the versioned warning/confirmation digest. The target is the original live Session, not a new Session. Only text input is eligible until other content has an independently verified preservation path. The model-facing message preserves the selected input's complete text; its source is exactly `{ kind: 'ds-bot-user-redo' }`, without role, work, exchange, sender, recovery IDs or recovery key. The separate journal, not that source string, proves identity and authorization.

Preparation is asynchronous and must complete a target-writer fixed-prefix check, current Session-object and scope/owner/membership checks, and a durable exact journal snapshot before admission. Recheck the same live objects, lease generation and permission at the admission boundary. An absent or inaccessible old record is not evidence that the original did not execute. Concurrent clicks on the same logical operation use the same IDs; a conflicting identity or uncertain prior state never creates a second operation.

## Single coordinator and claim

Only the Agent's existing shared guarded coordinator may authorize claims. Its `beforeTurnStart(session, input, turn)` is synchronous: it verifies the previously durable operation and current Session object and reserves the exact session object, turn, start sequence, message and admission ID in the process-local route. It does not append, do asynchronous I/O, consume pending/carry, or acknowledge execution. The matching `cancelTurnStart` removes only the exact still-provisional reservation; uncertain cleanup leaves it fenced. Host event handling accepts the registered start only if the store still maps the exact Session object, `session.eventAt(seq)` is the same event, and turn/sequence match; it deduplicates by exact Session object and sequence. The Handler must prevent ordinary pending, carry and interrupted-input injection from joining this redo. A callback that violates the synchronous contract or any changed identity yields unknown, never a successful admission.

The coordinator verifies the exact frozen input and the registration again at claim. A synchronous journal method durably records the stable operation as claiming before calling the provided single-use `claim()` callback. It may report a durable queued or claimed receipt only after the exact Session writer has confirmed the relevant events. Journal and Session log are separate persistence domains: a crash, thrown callback, missing writer, interrupted confirmation or conflicting receipt leaves the operation unknown and fenced, without changing IDs or automatically re-enqueuing. Other inputs must remain in their original queues and preserve their ordering.

## Result and restart

A completed turn is not a result receipt. A separately authorized result worker must bind the original operation to the exact new turn and fixed Session prefix, flush that same live writer, verify the complete prefix including the selected input/claim and turn end, and store the output or immutable authorized result reference with a digest and stable operation ID. The journal persists that result and its state atomically and durably before the user-facing view reports completion. An error, missing or mismatched prefix, session replacement, permission change, partial output or inability to prove the result is shown as unknown or failed; no automatic resend follows. Retries read the same operation receipt. Authorization is rechecked when a user reads the result. Never return the result to the original Bot sender or close, approve, or otherwise settle the original work.

After restart, in-memory registration is not evidence. The original journal and the fixed persistent Session prefix must uniquely identify the operation and its outcome. A missing record, mismatched Session incarnation, unavailable writer or inability to exclude duplicate side effects remains unknown. The Host must not infer a redo turn merely from `source.kind`; the special source only prevents it being mistaken for an ordinary pending input. History reconciliation must not replay the redo or settle unrelated pending IDs. A plugin reload during a running redo must not make its unfinished output eligible for ordinary routing.

## Validation still required

Exercise actual DS-Bot Host, the matching guarded Harness and a deterministic model in an isolated home. Cover duplicate clicks, registration and cancellation reentrancy, permission and Session replacement, changed queue candidates, interleaved ordinary work, process exit at each durable boundary, lost responses, repeated reads, restart history reconciliation and result authorization. Exercise ordinary Bot traffic too. A source-level or mock-authority test is not a durable end-to-end result. Generic `session/event` spoofing/republication is a separate known limitation: this contract relies on trusted in-process collaborators and exact Session/event checks, not a claim of process-wide plugin isolation.
